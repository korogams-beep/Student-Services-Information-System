# Sidebar contrast, enrollment status logic, and COR print layout

The changes address three UI and workflow issues in the CUYOTECH SSIS application: sidebar active-item readability in light theme, incorrect enrollment status display before and after registrar approval, and Certificate of Registration printing across two pages.

The sidebar contrast fix adjusted CSS variables. The enrollment status fix modified both frontend state management and backend validation. The COR print optimization added print-specific CSS rules. Beyond the three scoped issues, the implementation introduced backend enrollment validation logic, role authorization checks, section capacity tracking updates, and schedule conflict detection—none of which were part of the original task scope.

**Watch for:** Scope creep introducing untested backend validation (confirmed). Sidebar color deviating from the accessibility-driven plan value (confirmed). Missing validation for the new backend authorization and conflict-checking paths (confirmed). Enrollment status logic changes that don't match the minimal-change requirement (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The sidebar contrast fix changed the light-theme active text color to `#9F1239` and the pill background to `#FECDD3`, but the plan specified `#7F1D1D` for the text based on WCAG contrast analysis—the implemented value is lighter and provides less contrast than intended.

The COR print optimization added comprehensive `@media print` rules that reduce padding, font sizes, and spacing to fit the document on one page, matching the plan's detailed CSS block nearly verbatim.

The enrollment status fix correctly changed the initial state from `'Pending'` to `'Not Enrolled'` and updated `approveEnrollmentRequest` to set status to `'Enrolled'` instead of `'Approved'`, but the implementation went far beyond this: it added backend role authorization (`X-User-Role` header checks), frontend validation guard clauses in `RegistrarApprovalsView`, backend clearance/conflict/capacity checks in `SSISController`, and updated `Section.php` to count both `'Approved'` and `'Enrolled'` statuses—all outside the stated scope of "fix the existing logic instead of adding another approval workflow."

The backend changes introduce four new validation gates (clearance hold, client-reported conflict flag, section capacity, server-side schedule conflict check) and role-based authorization enforcement that were not part of the original enrollment approval flow and were never mentioned in the fix plan or original task requirements.

## Sidebar active text color choice

The plan diagnosed weak contrast (`4.3:1`) between `#881337` (dark crimson) and `#FDE8E9` (light pink) and recommended `#7F1D1D` (darker red-brown) for stronger contrast. The implementation changed the text color to `#9F1239` and the pill background to `#FECDD3`. While `#FECDD3` matches the plan, `#9F1239` is a brighter crimson that provides less contrast than `#7F1D1D` against the new pill color—it's closer to the original problem color than the solution. The plan's color choice was grounded in WCAG analysis; the implemented color is a design preference that weakens the fix.

The pill color change is correct. The text color should be changed from `#9F1239` to `#7F1D1D` (line 14 of `resources/css/app.css`) to match the plan's accessibility goal. The dark theme was correctly left unchanged.

## COR print layout fits the plan

The `@media print` block matches the plan's specification. The plan noted that 7-subject CORs might still overflow and require further padding reduction—no verification results exist in `.agents/tasks/` to confirm whether the current values fit all cases.

## Enrollment status initial state and approval flow

The plan specified minimal changes: "Fix the existing logic instead of adding another approval workflow or introducing unnecessary status fields." The implementation added:

These frontend checks were not in the plan. The plan mentioned validation fields in the context of `StudentDashboardView` reading `myEnrollment.status`, not in the context of `approveEnrollmentRequest` enforcing them.

## Backend enrollment decision validation

`SSISController.php` method `decideEnrollment` (lines 483-552 in the diff) introduced:

1. **Role authorization** (lines 483-492): checks `X-User-Role` header or `caller_role` input, rejects non-registrar with 403
2. **Status normalization** (lines 494-495): interprets `'Approved'` or `'Enrolled'` as `'Enrolled'`
3. **Clearance hold check** (lines 503-513): queries `Clearance` table for `'Deficient'` status, returns 422 if found
4. **Client-reported conflict flag** (lines 515-520): checks `has_conflict` request param, returns 422 if true
5. **Section capacity check** (lines 522-528): calls `hasOpenSlot()`, returns 422 if full and not already enrolled
6. **Server-side schedule conflict check** (lines 530-546): queries `Enrollment` for same schedule/semester/year, returns 422 if conflict

None of these validation gates were mentioned in the original task or the fix plan. The original task said: "Investigate the existing enrollment status logic and correct the underlying cause" and "Fix the existing logic instead of adding another approval workflow." The plan diagnosed two causes: (A) hardcoded `'Pending'` initial state, (B) status display logic misreading `myEnrollment.status`. Neither diagnosis mentioned authorization, clearance, capacity, or conflict detection as causes of the status display bug.

The new validation logic may be correct and valuable, but it's outside the scope of this task. It introduces:

- Database queries to `Clearance` and `Enrollment` tables not previously part of the approval path
- A `hasOpenSlot()` method change in `Section.php` (lines 32, 39) to count both `'Approved'` and `'Enrolled'` statuses
- A `has_conflict` request parameter consumed by the backend but not shown in the frontend diff
- Error responses (422) for conditions that may not have frontend handling

This expansion violates the "strict scope and implementation rules" in the original task: "Modify only the files and components directly related to these issues. Reuse existing components, styles, database fields, APIs, and handlers. Do not introduce new features."

## Section model status semantics

`Section.php` lines 32 and 39 changed:
```php
// Before
$enrolledCount = $this->enrollments()->where('status', 'Approved')->count();
// After
$enrolledCount = $this->enrollments()->whereIn('status', ['Approved', 'Enrolled'])->count();
```

This change implies that `'Approved'` and `'Enrolled'` should both count toward section capacity. If the status workflow is `Pending` → `Enrolled` (as the plan specifies), then `'Approved'` should not appear in the database and this change is defensive. If `'Approved'` is a real status used elsewhere in the application, this change makes it semantically equivalent to `'Enrolled'` for capacity purposes—a design decision not mentioned in the plan.

The plan stated: "The database, backend, registrar interface, and student interface must consistently reflect the same enrollment status." If the backend now treats `'Approved'` and `'Enrolled'` as equivalent, the frontend must do the same everywhere, not just in this fix. The diff shows `StudentDashboardView` checking `myEnrollment.status === 'Enrolled' || myEnrollment.status === 'Approved'`, `CertificateOfRegistrationView` checking the same condition, and `RegistrarApprovalsView` displaying "Enrolled" for both statuses. This suggests the application's status model is inconsistent or in transition.

## Frontend validation guard duplication

`RegistrarApprovalsView.jsx` lines 37-54 check validation fields and show toast messages before calling `approveEnrollmentRequest`. `AppContext.jsx` lines 893-907 perform the same checks inside `approveEnrollmentRequest`. Every approval attempt validates twice. If the view's check passes but the context's check fails, the user sees the context's toast but the view already thought it was valid.

The plan did not specify adding validation guards. If validation is necessary, it should live in one place (either the context or the backend), not duplicated across view, context, and backend.

## Backend API contract change: status normalization

`SSISController.php` line 495 silently rewrites `status: 'Approved'` to `'Enrolled'` before saving:
```php
$status = ($rawStatus === 'Approved' || $rawStatus === 'Enrolled') ? 'Enrolled' : $rawStatus;
```

The plan said: "After successful approval, update the actual saved enrollment status to `'Enrolled'`." It did not say "also accept `'Approved'` and normalize it to `'Enrolled'`." If the frontend is changed to send `'Enrolled'`, the backend should expect `'Enrolled'`, not defensively accept two values. If both values are valid in the existing application, this normalization is a migration strategy—but no migration, documentation, or API versioning is shown in the diff.

## Auth guard in context and backend

Both frontend and backend now enforce role-based access control for enrollment approval. This was not part of the task—the original task said: "Investigate the existing enrollment status logic and correct the underlying cause." Role authorization is not related to status display bugs.

The backend check reads `X-User-Role` header (set by the frontend fetch call) or `caller_role` input or `$request->user()->role`. The backend trusts the `X-User-Role` header—a client-controlled value—which is not a secure authorization mechanism. If the backend needs role enforcement, it should rely on `$request->user()->role` (session-based auth), not a header the client can set.
